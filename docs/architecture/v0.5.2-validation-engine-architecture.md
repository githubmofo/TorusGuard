# TorusGuard v0.5.2 Validation Engine & Deterministic Replay Architecture

## 🎯 Release Vision & Theme

**TorusGuard v0.5.2 Theme:** *“Prove the finding, replay the result, and regress with confidence.”*

v0.5.2 builds the proof infrastructure of TorusGuard, ensuring that all detection rules and guidance are backed by deterministic fixture replays, paired differential analysis, automated regression baselines, and root-cause diagnostic capabilities.

---

## 🏛️ 1. Validation Engine Layered Architecture

The Validation Engine is structured into 7 clean, decoupled layers (`harness/engine/`):

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                           7. Report Emitter                                 │
│  Renders deterministic Markdown & JSON reports for CI/CD and release audits  │
├─────────────────────────────────────────────────────────────────────────────┤
│                         6. Evidence Collector                               │
│  Captures environment snapshots, execution hashes, and runtime traces       │
├─────────────────────────────────────────────────────────────────────────────┤
│                      5. False-Positive Analyzer                             │
│  Diagnoses rule mismatches, weak evidence signals, and remediation actions  │
├─────────────────────────────────────────────────────────────────────────────┤
│                        4. Regression Tracker                                │
│  Asserts historical test case integrity across prior releases (v0.4.1+)     │
├─────────────────────────────────────────────────────────────────────────────┤
│                        3. Result Comparator                                 │
│  Differential analysis: Vulnerable Confirmed vs Hardened Safe validation   │
├─────────────────────────────────────────────────────────────────────────────┤
│                         2. Replay Runner                                    │
│  Multi-pass deterministic execution verifying identical output hashes       │
├─────────────────────────────────────────────────────────────────────────────┤
│                        1. Fixture Manager                                   │
│  Indexes structured test fixtures, vulnerable/hardened pairs, and schemas   │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 📋 2. Structured Fixture Definition Schema (`schemas/fixture.schema.json`)

Every validation fixture conforms to a strict JSON schema:
- **`fixture_id`:** Unique identifier (e.g. `TG-FIX-django-idor-scoping`).
- **`framework`:** Target framework (Django, DRF, FastAPI, Flask, SQLAlchemy, Express, Next.js).
- **`scenario`:** Architectural context under test.
- **`target_rule_id`:** Canonical rule ID evaluated (`TG-*`).
- **`vulnerable_variant`:** Path, code pattern, and expected finding count (> 0).
- **`hardened_variant`:** Path, safe code pattern, and expected finding count (= 0).
- **`verification_criteria`:** Reproduction command and expected diff summary.

---

## 🔁 3. Deterministic Replay Mechanics (`ReplayRunner`)

To prove finding consistency, the `ReplayRunner` executes each fixture across **3 independent evaluation passes**:
1. Computes the SHA-256 hash of the serialized scan output for each pass.
2. Asserts that $\text{Hash}_1 = \text{Hash}_2 = \text{Hash}_3$.
3. If any variation is observed, the replay is flagged as non-deterministic and marked for human investigation.

## ⚖️ 4. Paired Differential Comparison & Outcome Labels

The `ResultComparator` evaluates paired vulnerable and hardened fixture runs:

```text
┌───────────────────────────┬──────────────────────────┬───────────────────────────────┐
│ Vulnerable Target Status  │  Hardened Target Status  │        Computed Outcome       │
├───────────────────────────┼──────────────────────────┼───────────────────────────────┤
│ Findings Triggered (> 0)  │  Clean / 0 Findings      │  🔒 Vulnerable Confirmed      │
│ Findings Triggered (> 0)  │  Findings Triggered (> 0)│  🔴 False Positive            │
│ 0 Findings (Missed)       │  Clean / 0 Findings      │  🔴 False Negative            │
│ Unclear / Out-of-band     │  Unclear / Out-of-band   │  🔍 Needs Review              │
│ Previously Fixed Failed   │  N/A                     │  ⚠️ Regression Detected       │
└───────────────────────────┴──────────────────────────┴───────────────────────────────┘
```

## 🔄 5. Historical Regression Tracking (`RegressionTracker`)

Maintains baseline regression records for prior fixes (e.g., v0.4.1 issue fixes):
- **`REG-041-001` (`TG-AUTH-007`):** Service-layer authorization delegation in Django views.
- **`REG-041-002` (`TG-AUTH-006`):** Serializers with explicit `read_only_fields` in DRF.
- **`REG-041-003` (`TG-RATE-003`):** Missing pagination limits in DRF ViewSets.
- **`REG-041-004` (`TG-SSRF-001`):** Unchecked outbound HTTP fetch in FastAPI.
- **`REG-041-005` (`TG-INPUT-002`):** Parameterized `text()` bindings in SQLAlchemy.
