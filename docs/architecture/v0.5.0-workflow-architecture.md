# TorusGuard v0.5.0 Workflow Architecture Specification

## 🎯 Architectural Vision

TorusGuard v0.5.0 transforms TorusGuard from a static rule guidance library into a structured, evidence-backed **Security Workflow Engine** for AI coding agents and development teams.

Inspired by **OWASP ASVS** verification discipline and **NIST SP 800-218 Secure Software Development Framework (SSDF)** practices, v0.5.0 introduces:
1. A formal **6-Stage Finding Lifecycle** (`Detect` ──► `Classify` ──► `Verify` ──► `Remediate` ──► `Re-check` ──► `Archive`).
2. A **Normalized Finding and Evidence Schema** (`schemas/`).
3. Explicit **Evidence Typing** (`source`, `runtime`, `test`, `manual_review`).
4. An automated, repeatable **Validation Harness** (`harness/runner.py`).
5. A modular foundation designed for predictable incremental releases (`v0.5.1` – `v0.5.4`).

## 🔄 The 6-Stage Finding Lifecycle

Every candidate security finding moves deterministically through six distinct operational states:

```text
┌───────────┐     ┌────────────┐     ┌───────────┐     ┌─────────────┐     ┌───────────┐     ┌───────────┐
│ 1. Detect │ ──► │ 2.Classify │ ──► │ 3. Verify │ ──► │ 4.Remediate │ ──► │ 5.Recheck │ ──► │ 6.Archive │
└───────────┘     └────────────┘     └───────────┘     └─────────────┘     └───────────┘     └───────────┘
```

### Stage 1: Detect
- **Objective:** Locate potential vulnerability patterns across source files, package manifests, and configuration files.
- **Output:** Raw code candidate and initial file/line coordinates.

### Stage 2: Classify
- **Objective:** Map candidate to a canonical TorusGuard Rule ID (`TG-*`), taxonomy category, risk severity, and initial confidence.
- **Output:** Preliminary normalized finding object in state `IN_VERIFICATION`.

### Stage 3: Verify
- **Objective:** Prove data flow reachability and evaluate evidence sufficiency.
- **Evidence Rule:** If evidence is indirect or delegated to out-of-band architecture (e.g. domain service layers, reverse proxy headers), confidence is strictly set to `Needs Review`.

### Stage 4: Remediate
- **Objective:** Generate a least-invasive, framework-native code patch with explicit before/after diffs.
- **Output:** Remediation object with problem statement, risk explanation, and step-by-step verification commands.

### Stage 5: Re-check
- **Objective:** Execute differential static analysis against the modified codebase.
- **Assertion:** If the safe pattern is detected and the unsafe pattern is eradicated, status transitions to `Verified Safe` / `Remediated`.

### Stage 6: Archive
- **Objective:** Store verified audit records with timestamped evidence artifacts in the repository audit trail for compliance.

## 📊 Normalized Taxonomy Categories

| Taxonomy Category | Slug | Scope |
|---|---|---|
| **Authentication & Authorization** | `authentication-authorization` | Passwords, sessions, JWT, RBAC, IDOR, mass assignment, object scoping |
| **Input Validation & Encoding** | `input-validation-encoding` | Server-side validation, raw SQL concatenation, XSS, code execution |
| **Data Access & ORM** | `data-access-orm` | SQLAlchemy, Django ORM, Supabase/Firebase credentials, tenant scoping |
| **File & Upload Handling** | `file-upload-handling` | Path traversal, filename sanitization, file size limits, MIME types |
| **Secrets & Configuration** | `secrets-configuration` | Hardcoded keys, environment secrets, `.env` exposure, sensitive logs |
| **Supply Chain & Dependencies** | `dependency-supply-chain` | Pinned lockfiles, `pip-audit`, unpinned CI actions, install scripts |
| **Network & SSRF Boundaries** | `network-ssrf-boundaries` | Outbound request destination validation, webhooks, WebSockets |
| **Business Logic & Rate Limits** | `business-logic-rate-limiting` | Replay attacks, workflow state validation, brute-force throttling |
| **Client, Cache, & Platform** | `client-cache-platform` | Source maps, sensitive response caching, security headers, CORS |

## 🔒 Evidence & Confidence Model

```text
               ┌───────────────────────────────┐
               │    Evidence Modality Model    │
               └───────────────────────────────┘
                               │
       ┌───────────────┬───────┴───────┬───────────────┐
       ▼               ▼               ▼               ▼
┌──────────────┐┌──────────────┐┌──────────────┐┌──────────────┐
│    Source    ││   Runtime    ││     Test     ││    Manual    │
│   Evidence   ││   Evidence   ││   Evidence   ││    Review    │
│ (AST/Regex)  ││ (Logs/Header)││ (Assertions) ││ (Policy/IAM) │
└──────────────┘└──────────────┘└──────────────┘└──────────────┘
```

- **`Confirmed`:** Direct source evidence proves reachable, unmitigated vulnerability in the same module.
- **`Likely`:** Strong static indicators exist, but runtime environment configuration must be verified.
- **`Needs Review`:** The finding cannot be confirmed statically because it delegates control out-of-band (e.g. service layer, proxy header).
- **`Informational`:** Hardening recommendation or defense-in-depth best practice.

## 🧪 Validation Harness & Repeatability

The repeatable validation harness in `harness/runner.py` executes:
- **Schema Validation:** Verifies all JSON schemas and rule metadata.
- **Catalog Integrity:** Validates 60 unique `TG-*` rule IDs with 0 duplicates.
- **Differential Fixtures:** Tests vulnerable vs hardened pairs to verify that fixes eradicate findings deterministically.
- **Regression Suite:** Executes 10 paired regression fixtures across Python frameworks.
- **Lifecycle Assertions:** Validates state machine transitions and blocks illegal state jumps.
